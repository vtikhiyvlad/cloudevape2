# CloudVape — аудит и отчёт

Дата: 2026-10-26  
Стек: FastAPI + SQLAlchemy (async/PostgreSQL) + aiogram 3 + Jinja2 + Tailwind CDN  
Деплой: один Docker-контейнер на Render (API + бот)

---

## 1. Что это за система

Внутренний учёт склада и контроль продавцов **рядом с Эвотором** (фискальная касса).  
Не заменяет ОФД/фискализацию.

| Канал | Назначение |
|-------|------------|
| Telegram-бот | Регистрация, код входа, отчёты админу |
| Веб `/sell` | Касса продавца (телефон + камера штрихкода) |
| Веб-админка | Магазины, товары, продавцы, продажи, инвентаризации |
| Эвотор | Фискальные продажи (обмен номенклатуры через Excel) |

## 2. Что уже сделано (функционал)

### Магазины и доступ
- Несколько магазинов, изоляция данных
- Роли: owner / admin / seller / warehouse
- Привязка из Telegram + смена роли у уже привязанных
- Вход на сайт по одноразовому коду из бота (8 цифр, 3 мин, антиспам)

### Товары
- Категория → товар → варианты (2 характеристики + цена + остаток + штрихкод)
- Универсально: жидкости, одноразки, табак, устройства
- Excel-импорт (в т.ч. алиасы колонок «как из Эвотора»)
- Ручное добавление, правка цены/остатка в таблице
- Шаблон Excel

### Касса (веб)
- Каталог, категории, поиск
- Штрихкод: камера телефона + поле поиска
- Корзина, +/−, объединение позиций
- Атомарное списание остатка (FOR UPDATE)
- Сумма смены в шапке

### Инвентаризация
- Админ назначает период + группы
- Продавец вводит факт (≤ 1 раз в сутки)
- **Остатки сам продавец не меняет**
- Отчёт в Telegram админу + история на сайте
- Применение остатков — только owner/admin

### Прочее
- Фильтры продаж по магазину и дате
- Склад: остатки по всем точкам (роль warehouse)
- Low-stock уведомления после продажи
- Keep-alive /health + рекомендация cron-job.org
- Документ EVOTOR.md

## 3. Что улучшено в этом проходе (best practices)

### Backend
- Единый модуль ролей `app/core/roles.py` (источник правды для прав)
- Пул БД ограничен (pool_size=3) — адекватно free Postgres на Render
- `pool_pre_ping` + `pool_recycle` — меньше «мёртвых» соединений
- `get_db`: commit только при успехе, иначе rollback
- Health-check проверяет БД (`status: ok | degraded`)
- Session cookie: имя, TTL 12ч, SameSite=Lax
- Security headers: nosniff, DENY frame, Referrer-Policy, Permissions-Policy для камеры

### UX / UI
- Навигация зависит от роли (продавец не видит админ-разделы)
- Единые alert-блоки success/error
- Sticky nav, mobile-friendly касса

### Безопасность
- Продажи убраны из бота (меньше поверхности атаки)
- Одноразовые login-коды, инвалидация старых
- Инвентаризация: принцип разделения обязанностей (продавец считает, админ применяет)

### Данные
- Атомарные продажи через `create_sale` + StockMovement
- Уникальность инвентаризации 1 раз/день на продавца

## 4. Что сознательно упрощено / «убрано»

| Убрано / не делали | Почему |
|--------------------|--------|
| Продажи в Telegram | Логика: касса = веб с камерой |
| Автосмена остатков при сдаче инвентаризации | Только admin/owner |
| Отдельный Worker на Render | Free tier; API+бот в одном процессе |
| React/SPA | Для zero-code деплоя Jinja достаточно |
| Полноценный CSRF-token на все формы | Session + SameSite; усилить можно позже |
| Фискализация | Эвотор |

Файлы `bot/handlers/sales.py` и `stock.py` остались в репозитории, но **не подключены** к боту.

## 5. Чего ещё не хватает (бэклог по приоритету)

### Высокий
1. **Возврат по чеку** в веб-кассе (без фискализации, только склад)
2. **Нал/карта** на чеке + сверка смены
3. **Закрытие смены** с отчётом в Telegram
4. **Тесты** на `create_sale` и инвентаризацию (сейчас регрессии ловятся руками)
5. **Миграции Alembic в проде** вместо `create_all` + сырых ALTER

### Средний
6. Приход товара (закупка) и закупочная цена / маржа  
7. Перемещение между магазинами  
8. Маппинг «файл Эвотора → наш шаблон» одной кнопкой  
9. Пагинация длинных списков товаров/продаж  
10. CSRF-токены на POST-формы  

### Низкий / позже
11. API Эвотор (ночная синхронизация)  
12. Фото товаров  
13. PWA / «Добавить на экран» для кассы  
14. `https_only=True` для cookie на своём домене  
15. Structured logging (JSON) вместо print

## 6. Архитектурная оценка

| Критерий | Оценка | Комментарий |
|----------|--------|-------------|
| Под задачу (vape + Эвотор) | Хорошо | Не раздуто под «1С» |
| Защита остатков | Хорошо | FOR UPDATE + движения |
| Разделение прав | Средне+ | Роли есть, матрица прав ещё точечная |
| Качество кода main.py | Слабовато | ~1500 строк в одном файле — нужно дробить на routers |
| UI | Средне | Tailwind CDN, мобильная касса ок; нет дизайн-системы |
| Эксплуатация free Render | Ок | Один сервис + cron keep-alive |
| Тесты / CI | Нет | Риск при следующих правках |

**Главный техдолг:** разбить `main.py` на `routers/web_*.py` (auth, sell, inventory, sellers) — тогда проще сопровождать.

## 7. Рекомендации на ближайшие 2 недели

1. Задеплоить текущую сборку, прогнать сценарии: вход по коду → продажа → инвентаризация → применение админом  
2. Привязать Telegram владельца в Настройках  
3. cron-job.org → `/health` каждые 10 мин  
4. Выгрузка из Эвотора Excel → импорт в CloudVape  
5. Следующая фича в коде: **возврат + тип оплаты + закрытие смены**
